# Module map — Okolos P0–P5

Стадия 2 пайплайна. Правило: **каждый REQ ровно в одном модуле**; модули не
делят файлы; стадии 3→10 идут по одному кирпичу за раз.

## Walking skeleton (первым, до всего остального)

**M0 + M1 + тонкий срез M3/M4**: страница → детектор-заглушка → вердикт →
баннер → журнал → панель самоаудита, собранное под Chrome и Firefox, с
зелёным CI, где все гейты уже включены (пусть пока и проходят тривиально).

Смысл: сквозной путь существует и защищён гейтами до того, как появится
первая настоящая эвристика. Всё остальное потом наращивается внутрь готового
скелета, а не пристраивается к нему.

## Порядок и релизы

| Релиз | Модули | Что появляется у пользователя |
|---|---|---|
| R1 | M0 → M1 → M2 → M3 → M4 (+M14) | детект скрытых инструкций, инспектор, первый запуск, панель самоаудита |
| R2 | M5 → M6 | санитайзер, гейт агента, попап, журнал и дифф, очередь ≤3 |
| R3 | M7 → M8 → M9 | подписанные фиды, блок фишинга, punycode, ClickFix, ловушки, защита ввода, загрузки |
| R4 | M10 → M11 | офлайн-пароли, мониторинг утечек, чеклист восстановления |
| R5 | M12 → M13 | расширения и дельты, воркер, публичный статус домена и апелляции |

## Правила границ

1. `core-*` не импортирует браузерные API — проверяется lint-правилом (REQ-01),
   а не договорённостью.
2. Никакие два модуля не пишут в один файл; общее живёт в `contracts` и
   меняется только в M0 с обновлением зависимых модулей в том же изменении.
3. Каждый модуль закрывается собственными тестами и своим гейтом из REQ-таблицы
   до перехода к следующему.
4. Сценарии из `docs/ux/scenarios.md` — приёмочные критерии модуля; статус
   сценария двигается `draft → validated → implemented` только по аудиту.
